1. 起動スタックの全体像：なぜ 7 層もあるのか

端末で nikke と打ってからゲーム画面が出るまでに、プロセスは 7 つの層を通過する。 各層は「下の層が保証しないこと」をひとつずつ埋めるために存在しており、どれも飾りではない。 まず全体を眺めてから、層ごとに「何を保証するか」を見る。

① nikke（nix ラッパー） packages.nix が生成
nix store 内の dwproton の絶対パスを NIKKE_PROTON として注入し、nikke.sh を起動する。パスの解決だけを担う薄い層。
↓ exec
② nikke.sh（監視ラッパー） home-manager/desktop/nikke/nikke.sh
ACE（アンチチート）の初期化レースに対する運用対策の層。Steam 常駐の健全化、レジストリ tweak、起動リトライ、ウォッチドッグを担う。下の層のどれも「起動が確率的に失敗する」ことへの対処を持たないため、この層が生まれた。
↓ setsid + 起動
③ steam-run（FHS 環境 / bwrap） nixpkgs
NixOS には /usr/lib のような FHS 配置が無い。bubblewrap で「普通の Linux に見える」名前空間を作り、FHS を前提とする umu / Steam Runtime を動かせるようにする。NixOS 固有の層。
↓
④ umu-run（umu-launcher） nixpkgs
「Steam の外で Proton を使う」ための標準ランチャー。Steam Runtime のダウンロード・更新、GAMEID（umu-nikke）に基づく protonfix の適用、Proton の起動引数の組み立てを担う。
↓
⑤ pressure-vessel + steamrt4（Steam Linux Runtime） Valve
もう一段のコンテナ。ホストの glibc やライブラリのバージョン差を隠し、Proton が想定する固定のライブラリ環境（sniper/steamrt4）を提供する。ゲームのプロセスはこの中の PID 名前空間で動くため、ホストの pgrep から wine プロセスの一部が見えなくなる。
↓
⑥ dwproton（Proton fork = wine 本体） Dawn Winery / nix 管理
Windows API を Linux 上に実装する層。プロセス起動時に protonfix（umu-nikke.py）を実行し、wineserver・services.exe 等の wine 基盤プロセスを立ち上げる。今回のデッドロックはこの層の同期実装（fsync）で起きた。
↓
⑦ nikke_launcher.exe → nikke.exe + ACE Tencent / Level Infinite
Windows バイナリの世界。ランチャー（TCLS 系）が自己更新とゲーム起動を担い、ACE（AntiCheatExpert）がゲームと並走する。ランチャー本体のロジックは base.dll に置かれ、exe は薄いシェルになっている。
覚え方：①〜②が「このリポジトリの持ち物」、③が「NixOS の都合」、④〜⑤が「Steam エコシステムの都合」、⑥〜⑦が「Windows 互換の本体」。 問題調査のときは、症状がどの層の責務かをまず切り分ける。今回の例では「ウィンドウが出ない・CPU 0%」は⑦の症状に見えて、原因は⑥の同期実装だった。

2. wine の同期機構：4 世代の系譜

Windows のプログラムは、スレッド間・プロセス間の待ち合わせに カーネルオブジェクト（Event、Mutex、Semaphore）を使う。 SetEvent で旗を立て、WaitForSingleObject / WaitForMultipleObjects で旗が立つまで眠る、という仕組みで、 Windows カーネルは「signal した瞬間に待機中のスレッドを必ず起こす」ことを保証する。

wine はこの保証を Linux 上で再現しなければならない。その実装は 4 世代あり、速さと正しさのトレードオフの歴史になっている。

世代仕組み正しさ速さ備考
server sync
（wine 標準・最古）		 すべての待ち合わせを wineserver プロセスへのソケット RPC で行う 正しい 遅い 1 回の Wait ごとにプロセス間往復が発生する
esync オブジェクトを Linux の eventfd で表現し、カーネルを介して直接待つ ほぼ正しい（一部レースあり） 速い fd を大量消費する
fsync
（今回の主役）		 オブジェクトを共有メモリ上の整数で表現し、futex システムコールで待つ。カーネルはオブジェクトの意味を知らない 近似（レースあり） 最速級 Proton 系の既定。futex_waitv（カーネル 5.16+）を使う
ntsync / inproc sync
（wine 11 で本流入り）		 カーネルモジュール ntsync（/dev/ntsync）が Windows と同じ意味論のオブジェクトを提供する 正しい 速い fsync の作者自身による「正しさのための作り直し」

fsync が「近似」なのは、Windows カーネルが 1 命令でやること（signal と同時に待機者を解放する）を、 userspace の複数ステップ（値の書き換え → futex_wake）に分解しているからである。 分解されたステップの隙間には、別スレッドが割り込める。ほとんどのゲームではこの隙間が問題にならないが、 特定の同期パターンを使うプログラムでは致命傷になる。それが次章の主題である。

今の構成がどれを使っているかの確認方法：起動ログ（~/.local/share/nikke/umu.log）に fsync: up and running. と出ていれば fsync。 ntsync は /dev/ntsync が存在し、かつ fsync/esync を無効化したときに使われる（本機のカーネルは CONFIG_NTSYNC=m でモジュール未ロード、つまり現状は常に fsync）。

3. fsync の missed-wakeup レース：デッドロックの機構

fsync では、イベントは共有メモリ上の signaled という整数（0 = 未 signal、1 = signal 済み）で表現される。 待つ側（Waiter）は次の 2 段階で眠りに入る。 

// wine fsync の待機側（概略）
1. signaled をアトミックに読む      → 0 だった（まだ旗が立っていない）
2. futex_waitv(&signaled, 期待値=0) → 「値が 0 のままなら眠る」をカーネルに依頼

問題はステップ 1 と 2 の間である。ここに他スレッドの SetEvent と ResetEvent が連続して割り込むと、次のタイムラインが成立する。

Windows のカーネルイベントなら、②の時点で待機中スレッドは必ず解放される（Waiter は①の後もカーネルの待機キューに登録されてから眠るため、取りこぼしが構造的に起きない）。 fsync ではカーネルが「イベント」を知らず、ただの整数比較しかできないため、この保証を作れない。

なぜ「一か月無事」で「突然固まり」「リトライで直る」のか

①と④の間はマイクロ秒オーダーの短い窓であり、そこに②③の 2 操作がちょうど滑り込む必要がある。 つまり成立はスケジューリング次第の低確率事象で、これが症状の間欠性（一か月無事 → ある日突然 → 再起動 1 回で回復）をそのまま説明する。 そして NIKKE ランチャーの import テーブルには SetEvent / ResetEvent / WaitForMultipleObjects が並んでおり （nikke_launcher.exe と base.dll で確認）、まさにこのパターンを起動シーケンス最初期の内部同期に使っている。

dwproton に入っている緩和ハック

dwproton の ntdll.so を逆アセンブルすると、この種のレースへの緩和が既に実装されている。 fsync_help_simulated_pulse（Reset の直前に usleep(0) を挟み、Waiter に signal を観測させる猶予を与える）と fsync_yield_to_waiters の 2 つで、環境変数 WINE_FSYNC_HELP_SIMULATED_PULSE=1 / WINE_FSYNC_YIELD_TO_WAITERS=1 で有効化できる。 ただしどちらも .bss 配置＝既定値 0（無効）で、自動有効化は特定の Steam AppID（33460、別ゲーム）に限られる。 NIKKE の protonfix は AppID を意図的に削除するため、この経路にも乗らない。 つまり作者が用意した緩和が、NIKKE では一度も効いていなかった。 なお緩和は窓を狭めるだけで、ゼロにはできない（レースの成立条件自体は残るため）。

4. 今回のハングの診断根拠

2026-08-16 17:11 のハングしたセッションから採取した証拠と、それぞれが排除・支持する仮説を並べる。

観測事実意味するところ
ランチャープロセスが 16 分生存、CPU 時間 0 秒 ビジーループやネットワーク待ちではない。起動直後から一切実行が進んでいない
全 5 スレッドが futex 待ち
（futex_wait_multiple ×2、futex_do_wait ×3）		 futex_wait_multiple は fsync のオブジェクト待ち（futex_waitv）の待機点。残りはクリティカルセクション等で、fsync 待ちの 2 本に連鎖してブロックされた形
ウィンドウ 0 枚、intl_service 未起動 ウィンドウ生成・子プロセス起動より前、つまり初期化シーケンスの最初期で停止
自前ログが 270 バイト（ヘッダのみ）で停止 ログ初期化直後の内部同期で止まったことと整合
TCP ソケット無し サーバー応答待ち・認証待ち説を排除
直前の NixOS 世代切替はパッケージ変更ゼロ、steamrt4 は 8/14 更新後も 2 日間正常動作、Steam は起動 54 分 環境変化説（更新・常駐劣化）をすべて排除。残るのは確率的レース
nikke kill → 再起動 1 回で正常化 永続的な破損ではなく、タイミング依存の事象
nikke.sh のリトライが効かなかった理由：nikke.sh は「セッションが早期終了したら再試行」する設計で、 ACE 初期化失敗の従来モード（プロセスが死ぬ）には対応していた。 今回のモードはプロセスが死なずに固まるため、生存判定が「まだ起動中」と解釈し続け、リトライが一度も発火しなかった。 同じ根本原因（初期化のレース）が、別の故障モードで現れた形である。

5. dwproton という fork：誰が何を配っているのか

wine 系ソフトの系譜は fork の積み重ねでできている。dwproton の位置づけは次のとおり。

Dawn Winery は anime-games-launcher 周辺の開発者コミュニティで、企業ではない。 配布は自前の Forgejo インスタンス dawn.wine で行われ（GitHub に dawn-winery/dwproton-mirror というミラーがある）、 リリースは tar.xz のバイナリ配布である。リリース間隔は月に数回程度で、内容は「上流 proton-cachyos の追従」と「特定ゲームの修正」が中心になる。

protonfix（protonfixes/gamefixes-umu/umu-nikke.py）も dwproton に同梱されており、 NIKKE 向けには「Steam 検出の無効化」「NVAPI 無効化」「ランチャー自己更新の後始末（update_files/ の手動移動）」が実装されている。 つまり NIKKE を wine で動かすための知見の本体は dwproton 側に集約されており、nikke.sh はその外側の運用（リトライ・監視）だけを担っている。

6. nix 管理の実態と更新の流れ

dwproton は「nix 管理されていない」ように見えるが、実際は管理の形が他の依存と違うだけである。 このリポジトリの依存は 3 通りの経路で更新される。

経路対象更新の主体
flake input（flake.lock） nixpkgs、home-manager、hyprland など Renovate が lock 更新 PR を出し、CI 緑で auto-merge
nixpkgs 経由のパッケージ umu-launcher、steam-run など nixpkgs の更新に随伴（＝上と同じ Renovate 経路）
fetchurl 固定 derivation dwproton（home-manager/desktop/dwproton/default.nix） 手動。version と hash を書き換えて build

3 つ目の経路は「バージョンとハッシュをソースに直書きし、dawn.wine から取得して store に固定する」形で、 再現性は完全に保たれる一方、新リリースの検知が人力になる。 Renovate は dawn.wine（Forgejo）を既定では追跡しないため、11.0-5 のまま 6 リリース分置き去りになっていた。 これが「nix で管理していないのでは」という印象の正体である。 

# home-manager/desktop/dwproton/default.nix（更新後）
version = "11.0-11";
src = fetchurl {
  url = "https://dawn.wine/dawn-winery/dwproton/releases/download/dwproton-${version}/...";
  hash = "sha256-Xh4JgpLWHE7ilMRWta0n6Sc9rSkSl56/n8VvfGhJuxc=";
};

自動化したければ、Renovate の customManagers（regex マネージャ）＋ gitea-releases datasource で dawn.wine のリリースタグを追跡させ、version 行を PR で更新させる構成が組める（hash 更新は CI か手元で行う）。

7. 解決の選択肢と、それぞれが直すもの

最後に、検討した選択肢を「何を直すか」で整理する。重要な区別は、 レースの確率を下げる策とレースの土台を除去する策は別物だ、という点である。

選択肢直すもの評価
dwproton を 11.0-11 に更新
適用済み・switch 待ち		 NIKKE 関連の既知バグ（protonfix、自己更新まわり）と上流追従 やるべき基本整備。ただしfsync レース自体の修正は含まれない（新版バイナリで確認済み）
緩和フラグ有効化
WINE_FSYNC_HELP_SIMULATED_PULSE=1		 レースの確率（Reset 前に猶予を挟み窓を狭める） 1 行で済み副作用も小さいが、原理的にゼロにはならない
ntsync への切り替え
boot.kernelModules = ["ntsync"]
＋ PROTON_NO_FSYNC=1 PROTON_NO_ESYNC=1		 レースの土台（同期をカーネル調停の正しい実装に交換） 本筋。このハングのクラス全体が原理的に消える。ACE との相性が未検証なので、動作確認を挟んでから常用化する
nikke.sh にハング検出を追加 故障モードの後始末（固まったら畳んで再試行） 保険としては機能するが、スクリプトの複雑化を進める方向。ntsync が成立するなら不要になり得る

方針としては「⑥の層（wine の同期実装）で正しさを回復し、②の層（nikke.sh）の複雑さをこれ以上増やさない」が筋がよい。 nikke.sh の監視機構は「下の層が確率的に壊れる」ことへの補償として積み上がってきたものなので、 下の層が正しくなれば、対応する補償は削っていける。
